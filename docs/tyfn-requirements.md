# tyfn 컴파일러 — 요구사항 명세 (Draft 1)

> 이 문서는 인터뷰(질문-응답) 방식으로 도출된 요구사항을 정리한 것이다.
> 코드 작성 전 확정된 결정, 보류된 결정, 미해결 충돌을 구분해서 기록한다.
>
> - **확정**: 뒤집으려면 명시적 재논의가 필요한 결정
> - **방향**: 큰 방향만 합의됐고 세부는 미정
> - **보류**: 의도적으로 나중으로 미룬 주제
> - **충돌**: 서로 모순되거나 아직 답이 없는 지점 — 다음 라운드의 우선 안건

---

## 1. 목표 (Goals)

- 정적 타이핑 기반의 **범용 프로그래밍 언어** tyfn과 그 컴파일러를 만든다.
- **컴파일 실행**과 **인터프리터 실행**을 둘 다 정식으로 지원한다.
- 최종적으로 **네이티브 머신 코드** 수준의 성능을 낸다.
- 대부분의 모던 언어의 부분집합이 되는 **최소 문법**으로 웬만한 프로그램을 표현한다.
- 기존 언어 생태계(C/Rust로의 링크, Python/Kotlin/Go/TS로의 트랜스파일)와 **상호운용**한다.
- 키워드를 최대한 배제하고, **특수문자와 위치 규칙**으로 의미를 구분한다.
- **명령문(statement)을 없애고 모든 것을 표현식(expression)으로** 만든다.

## 2. 비목표 (Non-goals)

- 특정 도메인 전용 언어(DSL)를 만드는 것이 아니다.
- 동적 타이핑, 점진적 타이핑(gradual typing)은 지원하지 않는다.
- 자동 메모이제이션, 언어 전역의 지연 평가(Haskell식)는 도입하지 않는다.
- Mutex/Atomic 등 저수준 동시성 프리미티브를 사용자에게 노출하지 않는다.
- 별도의 헤더/선언 파일(C의 `.h`)을 사용자가 관리하게 하지 않는다.
- 빌드 매니페스트 파일(`Cargo.toml`, `go.mod` 등)을 요구하지 않는다.
- 한 가지 일을 하는 두 가지 방법을 만들지 않는다 (Python Zen).
- WASM을 트랜스파일 허브로 삼지 않는다 (§3.2 참조).

## 3. 실행 모델

### 3.1 확정

| 항목 | 결정 |
| --- | --- |
| 타이핑 | 정적 타이핑 |
| 실행 방식 | 컴파일 + 인터프리터, **둘 다 영구 정식 기능** |
| 인터프리터 용도 | 교육, REPL, 빠른 문법·산술 테스트 |
| 최종 백엔드 목표 | 네이티브 머신 코드 (C/Rust 타겟 또는 링크 가능한 산출물) |

### 3.2 백엔드 전략

- **자체 IR을 정의**하고, 각 백엔드가 그 IR을 소비하는 구조로 간다.
- WASM은 "여러 백엔드 중 하나"이며 **트랜스파일 허브가 아니다**.
  - 근거: `wasm2c`(WABT)로 WASM→C는 실무 수준으로 가능하지만, WASM→Python/Kotlin/Go/TS의 성숙한 디컴파일러는 사실상 없다. WASM은 저수준 스택 머신이라 고수준 구조(반복문, 타입, 시그니처)가 이미 소실된 상태이며, 복원하더라도 "숨겨진 WASM VM을 그 언어로 흉내낸 코드"가 되어 **생태계 접근성이라는 원래 목표를 달성하지 못한다**.
- 트랜스파일 대상(과도기 전략): Python, Kotlin, Go, TypeScript.
- 장기 비전: tyfn으로 언어 생태계 통일.

### 3.3 개발 순서

```
0단계  프론트엔드(렉서·파서·타입체커) + 트리워킹 인터프리터
1단계  자체 IR 설계
2단계  네이티브 백엔드 (C/Rust 유사 메모리 모델)
3단계~ WASM / 트랜스파일 백엔드
```

0단계는 버리는 작업이 아니라 이후 전부가 재사용하는 토대다 (jlox→clox 패턴).

### 3.4 CLI

```
tyfn            # REPL
tyfn a.ty       # 순수 컴파일 (바이너리 생성만, 실행은 별도)
```

- 서브커맨드(`build`, `compile`) 없음.
- 단일 파일 즉시 실행 모드 없음 — 실제 개발은 결국 다중 파일이므로 무의미하고, "컴파일 후 실행파일을 따로 실행"에 익숙해지는 편이 맞다.

## 4. 빌드 · 모듈 시스템

### 4.1 확정

- **매니페스트 파일 없음.** 진입점 파일 + import 그래프로 전체 프로젝트를 컴파일한다.
- 내부적으로는 **파일별 오브젝트 컴파일 + 링킹**. 증분 빌드 및 C/Rust 라이브러리와의 링크 호환성을 확보한다.
- **모듈 단위 = 파일 하나.** 디렉토리 단위(Go 패키지 방식)가 아니다.
  - 근거: 어떤 심볼이 어디서 왔는지 파일 하나만 보고 추적 가능해야 한다.
- **폴더 = 하위 파일을 필드로 갖는 구조체**로 취급한다. `folder.a.someFunc()`처럼 항상 명시적으로 접근한다.
- **파일 = 구조체 타입.** 모듈은 자동 인스턴스화되는 싱글턴이 아니라 타입이다.
  - `std.print(...)`처럼 모듈명으로 직접 호출 = 인스턴스 없는 static 호출.
  - 인스턴스별 가변 상태가 필요하면 구조체처럼 명시적으로 인스턴스화한다.
  - 모듈 함수가 모듈 변수를 바꿔도 **호출자에게만 보이는 변경**이며 원본 모듈에는 영향이 없다 (구조체 CoW 규칙과 동일).
- **별도 선언(헤더) 파일 없음.** 구현과 선언이 같은 `.ty` 파일에 공존하고, 컴파일러가 공개 시그니처를 내부 캐시로 자동 관리한다.
  - 근거: C/C++ 헤더 방식은 업계의 아웃라이어이며, 선언-구현 동기화 실패라는 버그 클래스를 만든다. C++20 Modules가 이를 벗어나려 도입된 기능이다.

### 4.2 순환 참조 · 초기화 순서

- **타입 간 순환 참조: 허용.** 2단계 컴파일(이름 수집 → 내용 채우기)로 자연 해결.
- **최상위 초기화 순서 문제: 원천 차단.**
  - 전역(모듈 최상위)에는 타입 / 상수 / 함수 / 변수를 둘 수 있으나,
  - **모든 초기값은 순수 상수 표현식이어야 한다.** 동적 함수 호출은 `>`로 만들어진 코드 블록 안에서만 가능하다.
  - 따라서 모듈 로드 시점에 "실행"되는 것이 없고, Python의 순환 import 문제가 발생하지 않는다.

## 5. 문법

### 5.1 선언과 리터럴 — 핵심 원리

**리터럴은 `타입 = 값` 쌍이다.** 그리고 선언은 `이름 : 리터럴`이다.

```
x : (int = 1)                    // 이름 : 리터럴
f : ((a: obj) obj = >{...})      // 이름 : 리터럴
    ((i: int) = >{...})          // 이름 없는 리터럴 = 익명 람다
```

- `:` 뒤는 통째로 하나의 리터럴이며, 이름의 타입은 리터럴의 타입 부분에서 따라온다.
- 이름을 떼면 그대로 익명 리터럴(값)이 된다 → **선언과 람다가 별개 문법이 아니라 같은 하나**.
- `=>`는 단일 토큰이 아니라 `=`(대입) + `>`(지연)의 분해다.
- C의 리터럴 접미사 체계를 대체한다:

| C | tyfn |
| --- | --- |
| `100LU` | `u64 = 100` |
| `1.0f` | `f32 = 1.0` |
| `'a'` | `char = 'a'` |

- 구조체 인스턴스화도 같은 형태로 통일된다 (`Person{}` vs `Person = {}` 같은 C++식 이중 표기를 피함). 스택/힙 할당 결정은 컴파일러가 문맥 규칙으로 처리한다.

### 5.2 블록과 지연 평가

| 표기 | 의미 |
| --- | --- |
| `{ ... }` | **즉시 평가**되는 블록 (IIFE). 내용에 따라 구조체 리터럴 또는 코드 블록 |
| `>{ ... }` | **지연**된 블록 = 함수/클로저 본문 |
| `> expr` | 지연된 단일 표현식 |

- 지연평가·메모이제이션은 `{}`에 없다. 필요하면 개발자가 직접 구현한다.
- **함수는 "블록"이 아니라 "클로저"**다. 구조체 안에 정의된 함수가 같은 구조체의 다른 필드를 참조할 수 있어, 별도 `class` 없이 메서드가 구현된다.
- 함수와 독립된 "그냥 블록값" 개념은 없다. `>{...}`는 함수 타입을 가지므로 값으로 쓰려면 호출(`>{...}()`)이 필요하고, 그럴 바엔 `{}`를 쓴다.

### 5.3 표현식 · 반환

- **모든 코드 블록은 표현식이다.** 마지막 줄이 묵시적 반환값.
- `<-` : **조기 반환 전용** 연산자 (`return` 대체). 전위형, 함수 본문 어디서든 사용 가능.
- 리턴 타입은 **기본 추론**, **재귀 함수만 명시 필수**.
  - 근거: 재귀는 fixpoint 추론이 필요해 닭-달걀 문제가 생긴다. TypeScript도 재귀 함수에는 사실상 명시를 요구한다.

### 5.4 가시성 · 가변성 — `.` 접두사

기본값은 public이며, `.`을 붙이면 "그 문맥에서 허용되는 만큼 최대한 제한"된다.

| 문맥 | `.` 없을 때 | `.` 붙이면 |
| --- | --- | --- |
| 모듈 최상위 데이터 | public | private (const는 이미 자동) |
| 모듈 최상위 함수 | public | private |
| 구조체 필드 | public, 외부에서 readonly | private + const |
| 함수 지역 변수 / 파라미터 | 이미 private, 스코프 내 가변 | const |

> ⚠️ **§9-C1 참조** — 기존 Tite 명세와 정면으로 충돌한다.

### 5.5 가변성 모델 (CoW)

- 구조체 필드도 함수 지역 변수도 관념적으로는 **const**이며, 프로그램 흐름에 따라 **복사본이 생기는** 것으로 본다 (컴파일러는 효율을 위해 실제 복사를 생략할 수 있다).
- 구조체 필드는 **외부에서 readonly**다. 변경은 같은 구조체 내부 메서드를 통해서만 가능하다.
- **대입식의 평가 결과**:
  - 순수 로컬 변수: 새로 대입된 값 자체
  - 상위 구조체의 필드: 그 구조체 전체 (갱신된 채로)
- 따라서 `a.changeX()`는 `a = a.changeX()`의 문법적 설탕이다. 실제 참조 공유가 아니므로 **스레드 간 데이터 레이스가 발생하지 않는다.**
- 함수 파라미터를 함수 안에서 바꿔도 호출자 원본에는 반영되지 않는다.

> ⚠️ **§9-C2 참조** — 필드 대입이 마지막 줄이 아닐 때의 규칙이 미확정.

### 5.6 파라미터 규칙

- **타입은 항상 명시**한다. 이름은 선택이다 (`이름: 타입` 원칙의 재사용).
- 파라미터 위치에서 **이름 없이 타입만** 쓰면 익명 파라미터가 된다: `(1) => {}`, `(2..5) => {}`.
- 따라서 `x => {}`에서 `x`는 **파라미터 이름이 아니라 타입**이다 (JS/TS와 다름).

```
[1,2,3].map (i: int) => print(i)     // 이름 있음
result.case (e: Error) => print(e)   // 페이로드 바인딩
result.case 1 => {}                  // 이름 없음 (타입만)
```

### 5.7 괄호 생략 규칙

> 인자가 **스스로 시작과 끝을 표시하는 리터럴**이면 호출 괄호를 생략할 수 있다.

대상: `>...`(지연), `{...}`(구조체), `[...]`(배열), `(params) => ...`(람다).

```
list.map((i:int) => {...})   →   list.map (i:int) => {...}
cond.then(>{...})            →   cond.then >{...}
```

맨몸 표현식(`f a + b`)은 여전히 괄호 필수 — Haskell식 우선순위 함정을 피한다.

### 5.8 조건 분기 · 패턴 매칭 — 하나의 메커니즘

`if`와 `match`는 별개가 아니다. `?`가 값을 **디스패치 뷰**로 바꾸고, 그 위에 메서드를 체이닝한다.

```
data?
    .then >{ ... }
    .else >{ ... }

data?
    .case A => { ... }
    .case B => { ... }
    .else >{ ... }
```

- `true`/`false`가 리터럴 타입이므로 **`.then`은 `.case true`의 설탕**이고, `.else`는 "아직 안 맞은 나머지 전부"다.
- `.case`는 매칭 대상(파라미터)이 있으므로 `=>`, `.else`는 없으므로 `>`.
- **순서 기반(먼저 맞는 게 승리).** 겹치는 조건과 범위를 쓸 수 있다.
- **exhaustiveness가 타입 문제로 환원된다**: `.else`가 없으면 결과 타입은 `T?`, `.else`를 붙이면 `T`.
  - 유니온: 모든 variant를 덮으면 컴파일러가 totality를 증명해 `?`를 제거한다.
  - 리터럴·범위(`int` 등): 전부 덮을 수 없으므로 `.else` 필수.
- 삼항연산자 `a ? b : c`는 **채택하지 않는다** (else 생략·else-if 체이닝·멀티라인 블록이 전부 부자연스러워짐).
- `if(cond)` / `match(value)` 같은 함수 형태도 채택하지 않는다 — 전역 이름을 차지하고 괄호 생략 규칙에 예외를 만든다.
- **구현**: 라이브러리 코드로 표현 가능하되, 컴파일러가 점프 테이블로 최적화하는 인라인/매크로 함수로 제공한다.

> ⚠️ **§9-C3 참조** — nullable에 대한 `?`의 의미가 미확정.

### 5.9 타입 표기

```
[]int        // int 배열 (접두 표기)
[str]int     // str → int 맵
()int        // int를 리턴하는 함수
()[]int      // 배열을 리턴하는 함수
[]()int      // 함수를 담는 배열
T?           // nullable
T | E        // 유니온
a: 1         // 리터럴 타입 (값 1만 허용)
x: 0..5      // 범위 타입 (타입 위치)
```

- 배열은 **접두 표기 `[]T`**. 후위 표기(`int[]`)는 `()int[]`가 "배열을 리턴하는 함수"인지 "함수를 담는 배열"인지 구분되지 않아 배제한다.
- **네이티브 컴파일 특성상 유니온은 런타임 discriminant 태그가 필요**하다 (문법은 TS식 `|`지만 내부 구조는 Rust의 태그드 enum과 동일).

### 5.10 범위 · 스프레드 · 타입 반전(reification)

```
0..5                 // Range 값 — exclusive (0,1,2,3,4)
(0..5).foreach (i: int) => print(i)
[...Color]           // Color의 모든 값을 배열로 → [Red, Green, Blue]
[...a, ...b]         // 배열 합치기
{...obj, x: 1}       // 구조체 병합
f(...args)           // 가변인자
```

- **`..`는 하나만 두고 exclusive**로 한다.
  - `..=`는 tyfn의 `이름: 타입 = 값` 형태와 충돌한다 (`x: 0..= 5`가 "`..=` 토큰"인지 "`..` 다음 `= 5` 대입"인지 모호).
  - `...`은 스프레드에 쓰이므로 Swift식 `0...5`도 불가.
  - TS/JS에는 범위 연산자가 없으므로 참조할 관습이 없고, 그들이 쓰는 `i < n` / `.slice(0, n)`이 모두 exclusive다.
  - inclusive가 필요하면 `0..n+1`. Python이 같은 선택을 했고 실사용에서 문제되지 않았다.
- **스프레드 `...`는 일반 기능**이다. `...T`는 게으른 시퀀스(할당 없음), `[...T]`는 대괄호가 "배열을 만들라"는 뜻이므로 materialize.
- 반전 가능한 타입은 **유한한 것뿐**이다 (enum, bool, 리터럴 유니온, 범위). `[...int]`, `[...str]`은 컴파일 에러.
- `[...0..5]`는 문법상 legal이지만 권장 표기가 아니다 (JS의 `[...[1,2,3]]`과 같은 위치). 순회는 `(0..5).foreach`.

### 5.11 반복

- **`while` 없음.** `.map` / `.foreach` / 재귀를 사용한다.
- `*`를 map 연산자로 쓰는 안은 배제 — 곱셈(특히 NumPy식 원소별 곱)과의 충돌이 크다.

## 6. 에러 처리 (방향)

- Result 계열 타입 + `?` 전파 연산자.
- `T | ErrorType` 유니온 + `.case` 판별 방식 검토 중.
- Nullable은 타입 시스템에 내장 (`T?`).
- "에러 있는 실패"(Result)와 "그냥 부재"(Option/nullable)를 구분한다.

> ⚠️ **§9-C3 참조** — `?`의 다중 의미가 충돌한다.

## 7. 동시성 (방향)

- **v1: 사실상 싱글스레드.**
- 최종 지향: **async/await + 이벤트루프/스레드풀**.
- 계층 구조:
  ```
  채널 / 메시지 패싱      (선택적 도구, 라이브러리 레벨)
  async/await             (사용자 레벨 기본)
  스레드 + 원자적 연산     (언어 기반, 사용자에게 비노출)
  ```
- Mutex/Atomic은 노출하지 않고, 내부적으로 필요한 곳은 atomic하게 동작한다.
  - 최적화 여지: 값이 실제로 스레드 경계를 넘는지 컴파일러가 추론해 atomic을 생략.
- **채널 send/receive = 콜스택을 넘나드는 return/파라미터 전달**로 취급한다. 값을 보내면 보내는 쪽은 접근권을 잃는다 (소유권 이전).
- `<-`는 **리턴 전용**으로 확정. 채널 문법은 generator/yield/async-await와 함께 나중에 재설계.

## 9. 미해결 충돌 (다음 라운드 우선 안건)

### C1. `.` 태그의 의미가 기존 Tite 명세와 정면 충돌

| | 기존 Tite (`readme.md`, `src/parser/tite.g4`) | 이번 인터뷰 |
| --- | --- | --- |
| 기본 가시성 | **private** | **public** |
| 기본 가변성 | **immutable** | 문맥별 (§5.4) |
| `.` | **public** | **private + const** |
| `$` | mutable | (미사용) |
| `#` | 타입 선언 | (미논의) |

`.`의 의미가 정반대다. 어느 쪽을 택할지 결정이 필요하며, `$`·`#` 태그를 tyfn에서 유지할지도 함께 정해야 한다.

### C2. `?` 후위 연산자의 다중 의미 충돌

같은 `값?` 형태에 세 가지 의미가 배정되어 있다:

1. **에러 전파** (§6) — `foo()?`가 실패 시 조기 반환
2. **디스패치 뷰 변환** (§5.8) — `cond?.then >{...}`
3. **옵셔널 체이닝 / 널 병합** — `user?.name`, `name ?? "익명"`

특히 2와 3은 `user?.then`과 `user?.name`이 **글자 그대로 같은 모양**이라, "멤버 이름이 `then`/`else`/`case`면 디스패치 뷰"라는 규칙이 필요해진다. 그러면 `then` 필드를 가진 구조체(예: Promise)가 깨진다.

또한 널 병합이 성립하지 않는다 — `?`가 순수 디스패치 뷰라면 `.case`를 하나도 안 썼을 때 전부가 "나머지"이므로 `name?.else > "익명"`이 값의 유무와 무관하게 항상 `"익명"`을 낸다.

**선택지**:
1. 옵셔널 체이닝 포기 (규칙은 하나가 되지만 TS/Kotlin 개발자가 가장 아쉬워할 문법이 사라짐)
2. 기능별로 기호 분리 (`?`는 디스패치 전용, 체이닝·병합은 다른 기호)
3. nullable에 한해 `?`가 "present 자동 매칭"으로 동작 (타입에 따라 의미가 갈리는 위험)

> "위치로 구분되면 안전, 타입으로 구분되면 위험"이라는 기존 기준에 따르면 3번이 위험군. **2번이 현실적 절충으로 보인다.**

### C3. 메서드 내 필드 대입이 마지막 줄이 아닐 때

```
changeX: () => {
    x += 1
    print("done")
}
```

마지막 줄이 `print("done")`이므로 묵시적 반환값은 그것이고, `x += 1`로 갱신된 self는 반환에 포함되지 않는다 → 호출자의 `a.x`가 안 바뀐다.

"필드 대입이 마지막 줄에 없으면 변경이 조용히 사라진다"는 함정이 되므로 규칙 확정이 필요하다.

### C4. Tite 문법 자산과의 정합성 검토

기존 `tite.g4`에 있으나 이번 인터뷰에서 다르게 결정되었거나 미논의인 것들:

- `? :` 삼항 조건 → 이번에 **배제** (§5.8)
- `..` / `..<` 둘 다 존재 → 이번에 **`..` 하나만, exclusive**로 결정 (§5.10)
- `|factor|` (절대값) → `|` 기반 범위 타입 표기가 불가능한 추가 근거
- `<A, B>` 매크로/제네릭 표기 → D2에서 다룰 것
- `:=` 타입 추론 표기 → §5.1의 `이름: = 값`과 관계 정리 필요
- `*` 접두 (import `*@stdio`, 루프 `* (i: 0..10 += 2) => {}`) → tyfn에서의 역할 미정
- `**` (거듭제곱), `//` (정수 나눗셈) 등 연산자 → D13

## 10. 완료 기준 (Definition of Done) — 0단계

0단계(프론트엔드 + 트리워킹 인터프리터)가 끝났다고 말하려면:

1. `tyfn`이 인자 없이 실행되면 REPL이 뜬다.
2. §5의 확정 문법을 파싱하는 렉서·파서가 있다.
3. 타입체커가 다음을 검증한다:
   - 정적 타입 일치, 리턴 타입 추론 (재귀 함수는 명시 요구)
   - 전역 초기값이 순수 상수 표현식인지
   - `.else` 없는 분기의 결과가 `T?`로 취급되는지
   - 유니온 매칭의 totality
4. 트리워킹 인터프리터가 §5.8의 분기/매칭, §5.5의 CoW 대입 의미론, `.map`/`.foreach`를 올바르게 실행한다.
5. 위 항목 각각에 대한 테스트가 있다.
6. §9의 충돌 C1~C4가 해소되어 이 문서에 반영되어 있다.

## 부록: 설계 원칙 (인터뷰에서 반복적으로 적용된 판단 기준)

1. **KISS** — 별도 서브커맨드, 매니페스트, 헤더 파일 등 부수 개념을 만들지 않는다.
2. **한 가지 일에 한 가지 방법** (Python Zen).
3. **위치로 구분하면 안전, 타입으로 구분하면 위험** — 같은 기호를 재사용할 때의 기준.
4. **암묵적 마법보다 명시성** — 단, 문제 해결에 본질적이지 않은 지엽적 요소는 숨겨 생산성을 확보한다.
5. **비용은 예측 가능해야 한다** — 저수준 성능 목표상 숨은 할당·숨은 분기를 만들지 않는다.
6. **기존 개발자의 직관을 우선한다** — 낯선 개념을 발명하기보다 익숙한 표기를 재조합한다.
7. **개념 수를 줄인다** — 새 규칙을 추가하기보다 기존 규칙의 조합으로 표현되는지 먼저 확인한다.
